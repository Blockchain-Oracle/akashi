---
title: Errors
description: Every error Akashi returns, when it happens and whether to retry.
---

An error is a JSON object with a 4xx status (5xx only for a bug on Akashi's side):

```json title="422 invalid_input (real)"
{
  "error": {
    "code": "invalid_input",
    "message": "Request body failed validation.",
    "retryable": false,
    "details": ["items: Field required"]
  }
}
```

`details` names each problem, with the field's path first.

| HTTP | `code` | When | Retry? |
|---|---|---|---|
| 400 | `invalid_json` | the body is not JSON | fix the body |
| 404 | `not_found` | no such path | check the path |
| 405 | `method_not_allowed` | the path exists, the method does not | use POST (GET for version and health) |
| 413 | `payload_too_large` | the body is over 64 KiB | send fewer items |
| 422 | `invalid_input` | valid JSON that fails validation | fix the fields named in `details` |
| 422 | `unsupported` | a request this deployment does not serve (stock quotes switched off) | no |
| 500 | `internal` | a bug in Akashi | yes, `retryable: true` |

<Callout title="Outages are not errors">
When an upstream source is slow or down, Akashi returns a `partial` success, not an error. See
[the response envelope](/docs/contract/response#reading-a-partial-answer).
</Callout>

Through the portal, payment problems come from the portal itself in the same shape, for example
`{"error": {"code": "PAYMENT_INVALID", "message": "The payment facilitator rejected this request.", "retryable": false}}`.
